# /pr

## Live context
- Branch: !`git branch --show-current 2>/dev/null || echo unknown`
- Base (guessed): !`git remote show origin 2>/dev/null | grep 'HEAD branch' | awk '{print $NF}' || echo main`
- Commits not on base: !`git log origin/main..HEAD --oneline 2>/dev/null || git log main..HEAD --oneline 2>/dev/null || true`
- Diff stat vs base: !`git diff --stat origin/main...HEAD 2>/dev/null || git diff --stat main...HEAD 2>/dev/null || true`
- gh available: !`command -v gh >/dev/null 2>&1 && echo yes || echo no`

## Task

### 1. Pre-flight
- If working tree has uncommitted changes, list them and ask whether to commit or stash first. Do not silently include uncommitted work in a PR.
- If the branch has no commits ahead of base, stop and tell the user there's nothing to PR.
- If `gh` is not available, fall back to printing the title and body the user can paste into the web UI.

### 2. Read the actual changes
- `git log <base>..HEAD --oneline` for the commit list.
- `git diff <base>...HEAD --stat` for the file-level scope.
- For non-trivial PRs, also read the full diff of the most significant files.

### 3. Write the PR description
Use this template. Fill it from the diff, not from imagination.

```
## Summary
<2-4 sentences. What changed and why. Reader has not seen the commits.>

## Changes
- <bullet per logical change, not per commit>
- ...

## Testing
- <commands run + results>
- <new tests added, if any>

## Risk
- <what could break, who's affected, what to watch after merge>

## Rollback
- <revert is fine / revert + run X / coordinated rollback because of migration Y>

## Screenshots
<only if UI changed; otherwise omit this section>
```

### 4. Title
Match the project's convention if there is one (check recent merged PRs: `gh pr list --state merged --limit 5`). Otherwise: same conventional-commits prefix as the commits, then a clear summary.

### 5. Open it
- Confirm title and body with the user.
- On approval: `gh pr create --base <base> --title "..." --body-file <temp>`.
- Default to **draft** PR if the user hasn't explicitly said "ready for review".
- After creation, print the PR URL.

### 6. Do not
- Do not `git push --force` to update an existing branch. If a push is needed, use `--force-with-lease` and only after confirming the remote branch state.
- Do not auto-assign reviewers or auto-merge.
- Do not include "🤖 Generated by Claude" footer unless the project's existing PRs include similar markers.

## $ARGUMENTS
Optional base branch. Defaults to the repo's default branch (usually `main`).
